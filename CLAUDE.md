# Stepswitch: working rules for Claude Code

Renamed from the placeholder "Switchyard" (CLI `sy`) after the Phase 0 name check (ADR 0001).

## Mission
An open-source, model-selective, multi-agent coding orchestrator. It routes every task, and every
step inside a task, to the best (model, harness) pair, works with any open-weight model and any
supported API format, verifies results with tests, and proves every public claim with `ssw prove`.
CPU-first: the core must be useful on an 8 GB laptop with tiny local models, and scale up to GPU
workstations and clusters.

## Sources of truth (read the section you need, never whole files)
- `docs/SPEC.md`: product spec, referenced as SPEC §N.
- `docs/PROGRESS.md`: phase status, decisions, open issues. Update at the end of every session.
- `docs/RESEARCH.md`: verified notes on external projects, formats, flags, model IDs and APIs.
- `docs/decisions/NNNN-title.md`: short ADRs, one per significant decision.
- `claims/claims.yaml`: every public claim, its exact wording, tests and evidence (SPEC §18).

## Hard rules
1. Verify before depending. Check every external repo, CLI flag, model ID, API format and chat
   template against current docs or source code before using it, and record it in RESEARCH.md
   with the date checked. If it can't be verified, isolate it behind an interface and mark it as
   an assumption.
2. All model access goes through the compatibility layer (`src/stepswitch/compat`, SPEC §4).
   No code outside it may assume a specific API format, chat template or tool-call syntax.
   Every model must also work through the fallback tool protocol.
3. Every public claim lives in `claims/claims.yaml` with a passing claim test. Never write a claim,
   superlative or number into the README or docs by hand; the claims section is generated by
   `ssw prove --render-readme` and shows only passing claims.
4. No company names anywhere: code, docs, comments, commit messages, examples, test data.
   Use product or model names only. Describe API formats generically ("chat-completions",
   "responses", "messages", "generate-content").
5. Nothing personal or machine-specific is committed. Endpoints, hostnames, keys and hardware
   overrides go in `.stepswitch/local.toml` (gitignored).
6. Zero telemetry. No network calls except to endpoints the user configured. All egress goes
   through `stepswitch.net` so it can be audited and blocked.
7. Every feature ships with tests. Science-track features also ship with numerical fixtures.
8. Core features must work CPU-only on 8 GB RAM using the tiny tier. GPUs are an upgrade, never
   a requirement.
9. Cross-platform: macOS, Linux, Windows. Use pathlib. No bash-only scripts in core paths;
   installers exist as both `install.sh` and `install.ps1`.
10. Tiny models (tier T0) never write or edit code in the science track. They classify,
    summarize, search and draft text only.

## Stack
- Core: Python >= 3.11, uv, Typer (`ssw`), FastAPI, Pydantic v2, SQLite in WAL mode, httpx.
- Dashboard: React + Vite + TypeScript, built to static assets served by the FastAPI app.
- Adapters for TypeScript harnesses live in `adapters/<name>/` as separate packages.
- Inference is always over HTTP to a model server or remote endpoint. Never import an inference
  engine into the core package.

## Token discipline for your own work on this repo
- Navigate with grep, symbols and view ranges. Don't read whole large files.
- Use subagents for research and wide searches. Bring back summaries, not raw dumps.
- Run the narrowest test that covers a change (`uv run pytest path::test -q`). Run the full suite
  only before a phase check.
- Keep this file under 120 lines. Detail belongs in docs/.
- At each phase boundary: update PROGRESS.md, commit, then compact the conversation.

## Workflow per phase
1. Read the SPEC section for the phase (SPEC §23 lists phases and their claims) and PROGRESS.md.
2. Extend `scripts/phase_check.py` and the claim tests for that phase first. They must fail.
3. Implement in small commits using conventional commit messages.
4. The phase is done only when all three pass:
   `uv run python scripts/phase_check.py <N>`, `uv run pytest -q`, and
   `uv run ssw prove --quick --phase <N>` (every claim assigned to the phase is passing).
   Record results in PROGRESS.md.
5. If research or implementation shows a SPEC assumption is wrong, write an ADR, pick the better
   option, note it in PROGRESS.md, and continue. Don't stall waiting for input.
6. If a claim can't be made true, narrow its wording in claims.yaml with an ADR. Never weaken the
   test to make it pass.

## Commands
- Tests: `uv run pytest -q` · Claim tests only: `uv run pytest tests/claims -q`
- Prove: `uv run ssw prove --quick` (add `--phase N`, `--claim C-0xx`, `--render-readme`)
- Lint and format: `uv run ruff check . --fix && uv run ruff format .`
- Types: `uv run mypy src`
- Phase check: `uv run python scripts/phase_check.py <N>` (add `--upto <N>` for phases 0..N)
- Dashboard: `cd dashboard && npm ci && npm run build`

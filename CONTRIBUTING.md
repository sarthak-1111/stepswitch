# Contributing to Stepswitch

Thank you for helping. This guide covers the ground rules, a development setup, and the most
useful kinds of contributions.

## Ground rules

These keep the project trustworthy. Pull requests that break them cannot be merged.

1. **Verify before depending.** Check every external repository, CLI flag, model ID, API
   format and chat template against its current docs or source, and record what you checked
   in [docs/RESEARCH.md](docs/RESEARCH.md) with the date. A fact you cannot verify goes behind
   an interface and is marked as an assumption.
2. **Model access goes through the compatibility layer** (`src/stepswitch/compat`). No other
   code may assume an API format, a chat template or a tool-call syntax, and every model must
   also work through the fallback tool protocol.
3. **Every public claim has a test.** Claims live in [claims/claims.yaml](claims/claims.yaml)
   with their exact wording and a claim test. The claims section of the README is generated by
   `ssw prove --render-readme`. Never write a claim, a superlative or a number into the README
   or the docs by hand.
4. **No company names** in code, docs, comments, commit messages, examples or test data. Use
   product and model names, and describe API formats generically ("chat-completions",
   "responses", "messages", "generate-content"). URLs and repository or model IDs are fine.
   `tests/unit/test_repo_hygiene.py` checks this.
5. **Nothing personal or machine-specific is committed.** Endpoints, host names, keys and
   hardware overrides belong in `.stepswitch/local.toml`, which is gitignored.
6. **Zero telemetry.** The only network calls go to endpoints the user configured, or happen
   in commands that download something on request. All of them go through `stepswitch.net`,
   so they can be audited and blocked.
7. **Every feature ships with tests.** Science-track features also ship numerical fixtures.
8. **CPU first.** Core features must work CPU-only on 8 GB of RAM with the tiny tier. A GPU is
   an upgrade, never a requirement.
9. **Cross-platform.** macOS, Linux and Windows. Use `pathlib`, and keep bash-only scripts out
   of core paths.
10. **Tiny models (tier T0) never write or edit code in the science track.** They classify,
    summarize, search and draft text only.

Significant decisions get a short ADR in [docs/decisions/](docs/decisions/).
[docs/SPEC.md](docs/SPEC.md) is the product spec, and [docs/PROGRESS.md](docs/PROGRESS.md)
records the state of each phase.

## Development setup

You need Python 3.11 or newer and [uv](https://docs.astral.sh/uv/).

```sh
uv sync --extra tokens          # the package, dev tools and exact token counting
uv run pytest -q                # the test suite
uv run ruff check . --fix && uv run ruff format .
uv run mypy src
```

Narrower runs are faster: `uv run pytest tests/unit/test_router.py -q`.

- **Claim tests:** `uv run pytest tests/claims -q`, or `uv run ssw prove --quick` to record
  evidence (add `--claim C-0xx` for one claim).
- **Dashboard:** `cd dashboard && npm ci && npm run build`. The browser smoke test needs
  `uv sync --group e2e`.
- **Docs site:** `uv sync --group docs`, then
  `uv run python -m sphinx -W --keep-going -b html docs/site docs/site/_build/html`. The pages
  are in `docs/site`; some show the README, the task API, the science.toml reference, the
  compatibility matrix or the examples, so edit those files rather than the page.
- **Demo:** `uv run python scripts/record_demo.py` records `docs/assets/demo.gif` (needs Docker,
  the CPU tier's models and Ollama with the demo's models; see the script).

Some tests use real models: the tiny CPU tier (`ssw models pull --tier cpu`) or a local model
server. They are skipped, with the reason, when what they need is missing.

## Good first contributions

- **Add a model.**
  1. Run `ssw models add <url-or-file>`, then `ssw probe` on it.
  2. Open a pull request with the registry entry and the probe result
     (`ssw probe --export <file>`).
  3. The compatibility matrix is generated from probe results, never written by hand.
- **Add a bench task.** A task is an entry in a suite file under `bench/suites/` (the
  instruction, the acceptance command, the track and tags) and a small repository under
  `bench/repos/<name>/`.
- **Add an API codec or an engine adapter.** Both sit behind small interfaces in
  `stepswitch.compat` and `stepswitch.serve`. Use the mock-server conformance tests as
  templates.
- **Improve a harness adapter.** Contract fixtures live in `tests/fixtures/harness/`. A fixture
  recorded from a live run is better than one built from documented shapes.

## Commits and pull requests

- Use [conventional commits](https://www.conventionalcommits.org/), for example
  `feat(router): …`, `fix(compat): …` or `docs: …`. The changelog is generated from them.
- Keep commits small and focused, with tests in the same commit as the change.
- Before you open a pull request, run the narrowest tests that cover your change, then
  `uv run ruff check .`, `uv run mypy src` and `uv run pytest tests/unit/test_repo_hygiene.py`.
- Describe what changed and how you tested it. Mention any claim, ADR or research note you
  touched.

## Code of conduct and security

Everyone taking part agrees to the [code of conduct](CODE_OF_CONDUCT.md). Report security
problems privately, as [SECURITY.md](SECURITY.md) describes, never in a public issue.
